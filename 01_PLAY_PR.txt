=======================================================================
0. BEFORE ANYTHING: WHAT IS THIS PR, AND WHAT DOES IT OWE?
=======================================================================
Skipping this step is the single most expensive mistake in this repo. A
task entering the corpus and a one-line oracle repair are reviewed against
completely different bars, and reviewing one against the other's bar
produces confident, wrong verdicts in both directions.

### THE DIFF IS THE SOURCE OF TRUTH. THE TITLE IS A HINT.

[RULE] Decide what a PR is by reading WHICH PATHS IT TOUCHES. A title is a
human's summary and can be wrong, stale, or copied from another PR. The
paths cannot lie about what the change does.

Get them, then reason:

    git show --name-only --format= <merge-or-head-sha>
    # or on an open PR, the Files-changed list

The shapes below are what the paths MEAN. They are not a closed list — a
kind you have not seen before is expected eventually, and the way to place
it is the same way these were placed: look at what the paths reach.

  reaches only `solution/` (± `tests/backend|frontend`, instruction.md)
      -> a REPAIR of an existing task. The task already exists and stays
         where it is.

  creates a whole `tasks/<state>/<slug>/` tree that did not exist
      -> the task is ENTERING the corpus.

  the same slug's files appear under a DIFFERENT `tasks/<state>/` than
  before (renames across state directories)
      -> a LIFECYCLE MOVE. The interesting part is the state it moves to,
         and what evidence justified it.
         If it moves tasks INTO tasks/approved/, this is the one shape
         that owes a stagehand verdict — see 00_CORPUS section 5.

  reaches only `qc/`, `.qc/`, `trajectories/` or `rewards/`
      -> an EVIDENCE filing. It is asserting a measurement, not changing a
         product.

  reaches `policy/`, `stacks/`, `tools/`, `.github/`
      -> INFRASTRUCTURE. It can change the rules every task is judged by,
         so its blast radius is the corpus, not a task.

A PR can be more than one of these at once. When it is, it owes the bar of
each thing it does — the bars add, they do not average.

### WHERE THE STAGE'S REQUIREMENTS ARE ACTUALLY WRITTEN

[RULE] DO NOT LEARN THE PER-STAGE REQUIREMENTS FROM THIS FILE. Learn where
they are written and read them there, at the revision the PR is on:

  policy/data/lifecycle.yaml   every state, what it means in its own words,
                               and which states it may move to. This is the
                               definition, not a description of it.
  policy/check-shape.sh        what a task tree may and may not contain,
                               per state. Exhaustive by design.
  .github/harbor-run-defaults.yml   the numeric bars a trial must clear.
  rubrics/task-implementation.toml  what the review gate actually grades.

Any sentence of the form "moving from A to B changes X into Y" is exactly
the sentence that rots when someone changes the pipeline. Those four files
are regenerated by the people who change it. Read them.

What is durable enough to state here is the SHAPE of the question, not its
answer:

  a task early in the lifecycle has had nothing vouch for its content yet,
  so what it owes is STRUCTURE and a working reference — not a measurement
  it has not been given the chance to earn.

  a task deep in the lifecycle is delivery-facing, so what it owes is the
  evidence its state claims it has.

  which states are which is in lifecycle.yaml's `evidence` list. Read it
  rather than trusting the sentence above to still be true.

### DO NOT DEMAND OF A PR WHAT ITS STAGE DOES NOT OWE

[RULE] Before you call something missing, establish that this KIND of PR
is supposed to carry it. The corpus has several stores that only some
kinds of change ever write to, and "the diff has no <X>" is a finding only
if PRs of this kind normally carry <X>.

The method, which does not go stale:

    for sha in $(git log --merges -60 --format=%H origin/main); do
      git show --name-only --format= "$sha" | grep -q '<the path you expect>' \
        && echo "$sha carries it"
    done

If comparable merged PRs do not carry it, your expectation is wrong, not
the PR. If they do, you have a real finding and a number to state it with.

[MECHANIC 2026-09-08, over ~160 merge commits on origin/main — REGENERATE
IT, DO NOT CITE IT] Counted this way at that date, repairs of an existing
task carried no trajectory or QC evidence at all, while PRs that moved a
task's state carried both. So on a repair, "there is no trajectory folder"
was not a finding. Whether that still holds is one loop away; run it.

### THE ANTI-LOOP CLAUSE — READ THIS BEFORE YOU USE MERGED PRACTICE

[RULE] Counting merged neighbours tells you what is PERMITTED here. It
NEVER tells you what is CORRECT.

A practice can be common and still wrong: everyone merged it, nobody
looked. So frequency is only ever a defence against inventing a
requirement — it is never a licence to break a stated one.

Concretely, and this is the failure mode to refuse:
  - "most merged PRs do X" DOES answer "is X allowed here?"
  - "most merged PRs do X" DOES NOT answer "is X right?" when X
    contradicts a rule that a script, a schema or a policy file enforces.
  - A rule with a checker behind it outranks any count. If the corpus and
    the checker disagree, that is a finding about the corpus.
  - Never cite a count to justify shipping something you can see is wrong.
    Say both: "N of M merged PRs do this, AND it violates <the rule>."

The loop this refuses: a mistake merges, becomes frequent, gets cited as
precedent, merges more. Frequency is evidence about permission. Rules are
evidence about correctness. Do not let the first overwrite the second.

[RULE] AND IT BINDS ON OPERATIONAL CHOICES, NOT ONLY ON TASK CONTENT.
The merge METHOD, the batch size, the cadence, the bar itself — those are
where "everyone here does it this way" feels least like a judgement and
most like a fact, which is exactly why it gets through. 00_CORPUS section
5 states the merge method for this reason: the repo's own habit is the
opposite of the rule, so the count will confidently tell you the wrong
thing.

### WHAT IS FIXED, AND WHAT YOU MUST GO AND CHECK

[RULE] Genuinely fixed, because a checker enforces each one:
  - the byte-pinned files may not be hand-edited (00_CORPUS section 1)
  - every criterion must fail on a nop (00_CORPUS section 3)
  - a task's tree is exhaustive: an ADDED file fails
These do not vary by stage or by PR kind.

[RULE] NOT fixed, and to be re-derived per PR:
  - which files of a task this kind of PR may touch
  - which evidence its stage owes
  - what the numeric bar is
For each, the authority is the file named above plus the merged-neighbour
count — in that order, with the rule winning.


=======================================================================
1. WHAT "DONE" MEANS — the whole definition, no more
=======================================================================

[RULE] DONE = the gates are green, there is no merge conflict, and there
is no open Cursor BUGBOT comment. That is the entire definition.

APPROVAL IS NOT PART OF IT.

[MECHANIC 2026-09-08] THE TRAP THAT WASTES THE MOST TIME: GitHub's
`mergeable_state: "blocked"` in this repo means ONLY "nobody has approved
it". Nothing here is a required status check, so a PR with every gate RED
and a PR with every gate GREEN both read `blocked`. The field is
therefore useless for readiness. Never report it as a blocker, never lead
with it, and never let it stand in for reading the checks.

When someone asks "is this ready", they are asking about THE CODE.
Answer with the gates. Which checks ARE gates is 00_CORPUS section 5 —
and note that a check being ABSENT is not the same as a check being red;
some gates only run on some kinds of PR.


=======================================================================
2. READ BEFORE YOU RUN
=======================================================================

[RULE] A merge-ready check is a READ. No /ci, no trial, no build, no
browser.

[SNAPSHOT] About a third of open PRs are already mergeable. The expensive
mistake is discovering that after spending an hour.

### The front door

  python3 -m tools.prreview status <PR>

That is the reading layer for PR verdicts, and it exists so you do not
parse a sticky or classify a check run yourself. Stdlib only, pure
functions over data. Its siblings:

  status <pr>            one PR's gate state and next action
  why-red <pr>...        the failing and pending checks
  passing                every PR whose recorded verdict passed
  oracle <slug>...       the task's oracle record, verbatim
  evidence --pr N        findings on the open migrate PRs
  review-verdict <f>     the task-review ladder over judge output

If you find yourself regex-ing a sticky comment, stop — that is what this
tool is for, and a hand-rolled reading of a sticky has been wrong before.

### Reading order, cheapest first

  1. prreview status. Often that is the whole job.
  2. If red: why-red, then the actual job log for the ONE failing layer.
  3. Only then: does it reproduce on main? (section 4)
  4. Only then: change anything.


=======================================================================
3. DO NOT INVENT GATES
=======================================================================

[RULE] Before calling X a blocker, prove X is absent from most recently
merged comparable PRs. The list of what is and is not a gate is in
00_CORPUS section 5; this section is about the HABIT, not the list.

Nearly every rule that has held this queue up turned out to be something
merged PRs carried routinely. The pattern is always the same: a reviewer
reads a doc, finds a requirement, and blocks on it without checking
whether the requirement is actually enforced in practice.

A known instance of the gap between doc and practice — NOTE it, do not
unilaterally start blocking on it:
  - the acceptance doc requires the oracle to pass >90% on the verifier,
    while a real share of merged HARD PRs shipped with Oracle FAILED

[RULE] But STILL USE JUDGEMENT. A frequency table cannot see a cross-user
data leak, or an oracle that does not implement its declared stack. Both
have been caught inside the numeric bar. NOTHING BLATANTLY INCORRECT
SHIPS — the frequency argument tells you what is not a blocker, it does
not tell you the code is right.


=======================================================================
4. REPRODUCE ON MAIN BEFORE YOU REPAIR
=======================================================================

[RULE] Establish whether a failure reproduces on main BEFORE fixing it.
Pre-existing corpus debt is a FINDING, not your repair.

This matters more than it sounds. The deterministic layers name
already-broken tasks on unscoped runs (00_CORPUS section 5, known-red
baseline). If you adopt one of those, you have widened a one-file PR into
corpus surgery, your PR now touches tasks nobody reviewed, and the
original change is buried.

How to establish it: run the same layer, scoped the same way, against
origin/main. The deterministic layers need nothing installed.

If it reproduces on main:
  - say so, precisely, naming the layer and the task
  - do NOT fix it inside this PR
  - the finding is worth filing on its own

If it does not reproduce: it is yours. Fix it.


=======================================================================
5. CURSOR BUGBOT — a finding must be CLEARED, not merely considered
=======================================================================

[RULE] Bugbot is not one of the graded gates, but an open Bugbot comment
BLOCKS. The bar is that THE COMMENT IS GONE.

Exactly two legitimate ways to clear one:
  1. the finding is RIGHT   -> fix it, push, resolve the thread
  2. the finding is WRONG or does not apply -> reply on the thread saying
     exactly why, THEN resolve it

Acting on a nonsensical finding is NOT required. Leaving it sitting there
IS a blocker. "I read it and disagreed" with the thread still open is a
FAIL, not a judgement call.

[MECHANIC] Bugbot findings on this corpus have a high false-positive rate
precisely because the corpus is deliberately uniform — see
`.cursor/BUGBOT.md`, which catalogues the intentional patterns that look
like bugs. Reading that file first often converts a "fix" into a
two-sentence reply.


=======================================================================
6. WHEN THE HEAD MOVES
=======================================================================
Which gates re-run on a push, and what `/ci` does, are in 00_CORPUS
section 5. What follows is what MOVING THE HEAD COSTS YOU.

[MECHANIC] Any push moves the head, and a verdict describes the commit it
names. So:
  - a count read off a stale sticky is NOT evidence
  - "Re-run all jobs" REPLAYS THE COMMIT THE RUN ORIGINALLY RAN ON. After
    a push it re-reports the verdict of the code that push replaced. It is
    not the same thing as re-checking the PR.
  - one recheck starts the graded gates for a bounded number of tasks and
    NAMES the rest.

[MECHANIC] Moving the head has a cost beyond runner minutes: it re-fires
the rubric judges. PRs have gone from 0 and 2 rubric failures to 4 on a
fresh run of unchanged content. NEVER TRADE A MERGE-READY PR FOR A
COSMETIC CHANGE WITHOUT SAYING SO OUT LOUD.

[RULE] RE-READ ON THE CURRENT HEAD before you claim anything is done. A
green claim on a stale SHA is the single most common false report here.
Name the SHA in your claim so the staleness is checkable.


=======================================================================
7. VALIDATE BEFORE YOU PUSH
=======================================================================

A push that turns CI red costs a cycle and the reviewer's trust.

  - run the deterministic layers for the tasks you touched, locally
  - for a CI fix: reproduce the ORIGINAL failure first, then show the
    same check passing
  - re-read your own diff adversarially — what would make CI reject this?
  - keep the fix MINIMAL: what the failure needs, no more. Do not widen
    the PR on your own initiative.

One validated push beats three speculative ones.

[RULE] Never force-push. Never rebase a shared branch. Never push to
main. Never merge, approve or close a PR. No draft PRs.
(If merging is ever lifted to you for a pass, it is a MERGE COMMIT —
00_CORPUS section 5. The lift names a population and expires with it.)

[RULE] Never hand-edit the byte-pinned files. The canonical list, and the
two manifests that ARE editable, are in 00_CORPUS section 1.

[MECHANIC] If a push is refused by the signature rule, use the repo's own
tool: tools/push_signed.py.


=======================================================================
8. WHEN TO STOP — a HOLD is a SUCCESS
=======================================================================

Stop and report, do not push through:

  two repair rounds on the SAME red check, still red
  two trials errored / cancelled / no REWARD line
  a run not terminal in about two hours
  the number flat, or moving AWAY, across two rounds
  a very large token spend with no valid measurement yet

A hold is a result. Report: what you changed, what proved it (or failed
to), the state you are leaving behind, what you did NOT verify.

### The handoff you leave

Whoever picks this up sees NOTHING you saw. Write for them:

  WHAT I CHANGED   files and lines, not intent
  THE PROOF        the command and its output, or "none"
  STATE            branch, head SHA, what is green and what is red
  NEXT             the single next action
  NOT VERIFIED     everything you assumed
